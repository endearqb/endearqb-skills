# 流程图与架构图的审美规则

> Skill 路径：`product-story-pptx/references/diagram-patterns.md`

流程图最容易暴露一份 deck 的“工程味”：节点尺寸不一、箭头拐弯、彩虹配色、文字塞满、线条交叉。好的图不是把所有系统关系都画出来，而是让观众在 3 秒内知道**方向、阶段和当前重点**。

## 1. 先判断是否需要图

使用流程/结构图，仅当内容存在：

- 明确顺序。
- 因果链。
- 分层关系。
- 输入—处理—输出。
- 3 个以上需要同时理解的节点。

不要画图：

- 只是 3 个并列优势：用 bullets 或 feature grid。
- 只有 A 与 B：用 compare。
- 主要问题是数值大小：用 chart。
- 需要展示真实界面：用 screenshot/feature hero。

## 2. 支持的四种结构

### Cards：阶段清楚、解释稍多

```text
[1 授权]  >  [2 建索引]  >  [3 原处提问]
```

- 3–7 个节点，3–5 最佳。
- 每个节点可有一行 desc。
- 当前关键步骤使用强调色。
- 适合产品工作流、实施步骤、服务流程。

### Chevron：动作连续、速度感更强

```text
[发现 >] [判断 >] [执行 >] [复盘 >]
```

- 3–6 个节点。
- label 置于箭头带内。
- desc 放下方，保持一行。
- 适合流水线、发布流程、转化漏斗的线性阶段。

### Vertical：时间或里程碑

```text
  1  试点
  │
  2  验证
  │
  3  扩展
```

- 适合 roadmap、实施计划、历史进程。
- 不要在一页画两条平行时间线。
- 里程碑超过 6 个时拆成“近期 / 中期”。

### Layers：架构与责任层级

```text
[体验层：问答 / 搜索 / 推荐]
[服务层：检索 / 权限 / 评估]
[数据层：文档 / 代码 / 对话]
```

- 3–5 层。
- 从用户可见层到底层支撑，或反向，但全页只用一个方向。
- 每层最多一个 label 和一句 caption。
- 不在层内再嵌套多级小盒子；复杂架构拆页渐进展示。
- 当右侧留白需要真实场景证据时，可在 `direction: vertical`、`style: layers` 的页面增加 `images`（1–3 张）；流程仍是主结构，图片只负责解释层级对应的现实语境。

## 3. 十条 taste 规则

1. **一个方向。** 左到右、上到下或底到顶，只选一个。
2. **一个高亮。** 当前步骤使用强调色，其他节点退到中性。
3. **节点等大等距。** 差异靠内容与高亮，不靠随意大小。
4. **标签短。** 使用动词短语，如“自动建索引”，不是完整段落。
5. **箭头退后。** 箭头比节点小、颜色更弱。
6. **不交叉。** 需要交叉就说明一页承担了太多关系。
7. **不彩虹。** 不用每个节点一种颜色。
8. **不依赖图例。** 位置、标题与高亮应该自解释。
9. **留白至少 25%。** 图不是把内容区填满。
10. **复杂关系渐进构建。** 复制同一图到 2–3 页，只移动高亮或增加一层。

## 4. 文字规则

- Label：中文 ≤ 6 字；英文 ≤ 3 词。
- Desc：一行，建议中文 ≤ 14 字。
- 横向 Cards / Chevron 的 Label 必须保持单行；编号与标签分开排版，不能依赖手工换行挤进箭头。
- 节点数：3–7。
- Highlight：恰好 1 个。
- Title：直接说流程带来的结论，例如“三级校验把错误挡在发布前”，而不是“工作流程”。

### 动词优先

| 名词标签 | 更好的动作标签 |
|---|---|
| 数据源 | 授权数据源 |
| 索引 | 自动建索引 |
| 查询 | 原处提问 |
| 评估 | 验证答案 |
| 部署 | 灰度上线 |

## 5. 颜色与形状

默认：

- 非高亮节点：`surface` 填充 + `rule` 描边。
- 高亮节点：`accent` 填充 + 自动选择深/浅文字。
- 箭头：`neutral_data`。
- 说明文字：`text_muted`。

形状：

- Cards：圆角矩形，轻微圆角，不加阴影。
- Chevron：连续箭头带，重叠统一。
- Timeline badge：圆形编号。
- Layers：同宽横向带。

禁止：

- 3D 立体块。
- 发光阴影。
- 渐变彩色节点。
- 不同圆角半径混用。
- 随机图标填充每个节点。

## 6. 为什么不用 Connector

`flow_diagram.py` 使用确定坐标的 chevron 或细矩形，不使用 PowerPoint connector：

- 不同渲染器对吸附点和折线路径处理可能不同。
- Connector 在节点尺寸变化后容易出现错位。
- 固定形状更容易 lint、复现和保持跨环境稳定。

箭头因此只是“方向提示”，节点编号才是主要的顺序保证。

## 7. 节点数量与响应式压缩

Cards 布局会根据节点数计算宽度：

- 3–4 节点：较大卡片，可容纳 label + desc。
- 5 节点：减少间隙，仍保持一行 desc。
- 6–7 节点：自动压缩，但应优先考虑 chevron 或拆页。

如果节点宽度不足，脚本会报错而不是生成无法阅读的图。

## 8. 渐进构建

需要解释复杂架构时，不在一页塞满：

### 页 1：只给全貌

标题：“答案先经过权限，再进入检索与生成。”

高亮“权限层”。

### 页 2：保持位置不变

标题：“检索阶段只返回用户有权访问的原文片段。”

高亮“检索层”。

### 页 3：保持位置不变

标题：“生成结果附出处，所以可以回到证据。”

高亮“答案层”。

位置不变降低认知负担，标题和高亮推动故事。

## 9. 架构图的抽象层级

不要把部署拓扑、业务模块、数据流和权限模型同时画在一张图上。先确定当前页的问题：

- 谁与谁交互？用 flow/hub（本 skill 当前不内置 hub，可用 cards 近似或扩展）。
- 数据如何流动？用 linear flow。
- 系统如何分层？用 layers。
- 何时发生？用 vertical。

一张图只回答一个问题。

## 10. 反模式与修正

| 反模式 | 根因 | 修正 |
|---|---|---|
| 12 个节点挤一页 | 把技术文档当演示页 | 拆成全貌 + 两页渐进 |
| 每节点不同颜色 | 没有决定重点 | 只高亮一个节点 |
| 箭头横竖混杂 | 同时画顺序与依赖 | 选择一种关系，另一种放下一页 |
| 节点内 4 行文字 | Label 在承担说明书职责 | 保留动作短语，解释交给讲者 |
| 图例解释颜色 | 颜色语义不直观 | 用位置与标题自解释 |
| 连接线抢过节点 | 把线路当视觉主体 | 减弱箭头，使用编号 |

## 11. Spec 示例

```yaml
- type: flow
  bleed: none
  energy: 3
  mood: 踏实
  label: 接入方式
  title: 三步接入，不改变现有工作流
  direction: horizontal
  style: cards
  steps:
    - label: 授权数据源
      desc: 飞书 / GitHub / Slack
    - label: 自动建索引
      desc: 首轮 30 分钟
      highlight: true
    - label: 原处提问
      desc: 无需切换窗口
```

## 12. QA

- 3 秒内能否说出阅读方向？
- 不看箭头，仅看编号是否仍能理解顺序？
- 高亮节点是否与 action title 对应？
- 节点是否等大等距？
- Label 是否是动作而不是名词？
- 箭头是否比节点更安静？
- 图缩到一半尺寸时是否仍可读？
- Layers 使用配图时，图片是否与层级语义互补，而不是装饰性重复？
