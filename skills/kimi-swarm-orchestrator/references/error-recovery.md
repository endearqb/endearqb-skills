# Error Recovery Reference — 错误恢复策略

本文档定义Swarm编排框架中所有可预见错误类型的恢复策略。Orchestrator在Phase 5监控中遇到问题时，按此文档执行恢复。

> **Error Recovery ≠ Refinement Loop**：本文档处理的是**失败**（Worker 没产出、超时、环境崩溃等），目标是让流程跑通；SKILL.md 的 `Refinement Loop` 处理的是**成功但不够好的产出**，目标是打磨质量。两者都受"有界"约束——错误恢复的重试上限为 2 次（见策略1），精炼回路的迭代上限默认 2、上限 3。不要把质量打磨伪装成错误重试来绕过上限。

## 错误分类

### 按层级分类

| 层级 | 影响范围 | 处理优先级 |
|------|----------|-----------|
| L1: 单个Worker失败 | 仅该Worker的产出 | 高 |
| L2: 多Worker同类失败 | 多个Worker的同类任务 | 紧急 |
| L3: 合并失败 | 整体产出无法集成 | 紧急 |
| L4: 环境/基础设施失败 | 所有Worker受影响 | 最高 |

### 按原因分类

| 原因类型 | 典型表现 | 可恢复性 |
|----------|----------|---------|
| 超时 | Worker在时限内未完成 | 高 |
| 资源耗尽 | 内存/磁盘/网络不足 | 中 |
| 逻辑错误 | Worker无法理解任务或执行错误 | 中 |
| 规划缺陷 | 规划文档导致Worker无法执行 | 需重新规划 |
| 环境错误 | 依赖缺失、权限不足 | 高 |
| 合并冲突 | 多Worker产出重叠或矛盾内容 | 高 |
| 外部依赖失败 | 第三方服务不可用 | 低 |

## 恢复策略

### 策略1: Worker重启 (Worker Restart)

**适用**：L1超时、L1资源耗尽、L1环境错误
**流程**：
1. 记录失败Worker的状态和已产出内容
2. 清理Worker的工作目录
3. 使用相同分支重新启动Worker
4. 如Worker已有部分产出，在新Worker指令中包含已完成的进度

**限制**：最多重试2次。第3次失败 → 升级至策略2。

**指令模板**：
```
你是Worker-{编号}的替代者。前任Worker因{原因}失败。

已完成的工作：
- {已完成的产出摘要}

你需要完成：
- {剩余任务}

请从{起始点}继续执行。
```

---

### 策略2: 任务重分配 (Task Redistribution)

**适用**：L1Worker3次重启仍失败、L2多Worker同类失败
**流程**：
1. 将失败Worker的任务拆分为更小的子任务
2. 分配给其他健康的Worker（如果其负载允许）
3. 或启动新的Worker接管

**负载检查**：重新分配前，确认目标Worker的当前任务量不超过原始分配的150%。

---

### 策略3: 规划修正 (Plan Correction)

**适用**：L2多Worker因规划缺陷失败、L3合并时发现结构性问题
**流程**：
1. 暂停所有Worker（记录当前状态）
2. 分析失败根因是否来自规划文档
3. 修正规划文档（更新plan.md）
4. 通知受影响Worker读取更新后的规划
5. 恢复执行

**约束**：规划修正只能在Phase 4（Worker执行阶段）进行。Phase 5-7发现问题时，应记录为下一迭代的改进项。

---

### 策略4: 降级执行 (Graceful Degradation)

**适用**：L4环境完全不可用、关键外部依赖持续失败
**流程**：
1. 评估是否可以跳过失败部分继续交付
2. 如果可以：标记失败部分为"未执行"，继续合并其余产出
3. 如果不可以：终止任务，向用户报告失败原因和已完成部分

**决策树**：
```
失败部分是否为核心交付物？
  ├─ 否 → 跳过，交付其余部分
  └─ 是 → 是否有替代方案？
       ├─ 是 → 使用替代方案
       └─ 否 → 终止任务，报告状态
```

---

### 策略5: 合并冲突解决 (Merge Conflict Resolution)

**适用**：L3 多Worker产出重叠或矛盾
**流程**：
1. 识别冲突文件和冲突类型
2. 逐文件解决：
   - **不同Worker编辑不同部分**：保留双方修改
   - **同一内容冲突**：选择更完整的版本，或合并两者内容
   - **文件命名冲突**：重命名后保留两者
3. 将解决后的内容写入 `output/` 目录

**冲突解决优先级**：
1. 保留Worker的完整产出（不丢失任何内容）
2. Scaffold的共享组件优先于Worker的修改
3. 当无法决定时，保留两个版本并标记为`_alt`

---

### 策略6: 环境重建 (Environment Rebuild)

**适用**：L4基础设施损坏、目录结构损坏
**流程**：
1. 备份已有产出（复制各 `dim{编号}/` 目录中的输出文件）
2. 重新创建目录结构（`dim{编号}/`、`shared/`、`output/`）
3. 恢复已备份的产出文件
4. 重新运行Scaffold（如需要）

## 恢复决策流程

```
错误发生
  │
  ▼
判断层级
  │
  ├─ L1 单Worker失败
  │     ├─ 超时/资源/环境 → 策略1 (Worker重启, 最多2次)
  │     ├─ 逻辑错误 → 策略3 (规划修正)
  │     └─ 3次重启仍失败 → 策略2 (任务重分配)
  │
  ├─ L2 多Worker失败
  │     ├─ 同类错误 → 策略3 (规划修正)
  │     └─ 不同错误 → 策略1逐个处理
  │
  ├─ L3 合并失败
  │     └─ 内容冲突 → 策略5 (冲突解决)
  │
  └─ L4 环境失败
        ├─ 可重建 → 策略6 (环境重建)
        └─ 不可恢复 → 策略4 (降级/终止)
```

## 预防性措施

### Worker指令设计原则

1. **原子性**：每个Worker的任务应尽可能独立，减少跨Worker依赖
2. **完整性**：Worker指令包含完成任务所需的全部信息，不依赖外部上下文
3. **边界明确**：清楚定义Worker不得修改的范围
4. **可验证性**：Worker产出应可通过文件检查验证

### 环境隔离检查清单

- [ ] 每个Worker有唯一的 `dim{编号}/` 目录
- [ ] `shared/` 目录已包含所有共享资源
- [ ] Worker无权限修改其他Worker的 `dim{编号}/` 目录
- [ ] Worker无权限修改 `shared/` 目录

### 监控检查点

| 检查点 | 时机 | 检查内容 |
|--------|------|---------|
| Worker启动确认 | Phase 4启动后5分钟 | Worker是否开始工作（是否有文件操作） |
| 中期进度 | Phase 4执行到50%时间 | Worker产出是否符合预期 |
| 完成确认 | Phase 4预计结束前 | 所有Worker是否已在 dim{编号}/ 产出文件 |
| 合并前检查 | Phase 6开始前 | 所有 dim{编号}/ 产出是否完整可合并 |

## 常见错误及解决方案速查

| 错误现象 | 可能原因 | 解决方案 |
|----------|----------|---------|
| Worker无输出文件 | 指令不清/Worker未启动 | 检查指令完整性，重启Worker |
| Worker修改了共享文件 | 边界定义不清 | 恢复共享文件，重新下发明确边界 |
| 合并时发现内容重叠 | Worker范围重叠 | 解决冲突后，下次任务调整范围划分 |
| 产出文件不在dim目录 | 未指定工作目录 | 在Worker指令中明确指定 dim{编号}/ 路径 |
| Worker写入了其他Worker的目录 | 边界不清 | 移动文件到正确目录，修正指令 |
| 产出文件为空 | Worker未正确保存 | 要求Worker在指令中明确文件保存步骤 |
| Worker循环重复工作 | 指令有歧义 | 策略3：修正规划文档，明确终止条件 |
